# TT の確保コストとライフサイクル

[転置表管理](transposition-table.md) が TT の**探索意味論** (持ち駒優越，len-aware
エントリ，GC) を扱うのに対し，本節は TT を**いつ・どれだけ・どのように確保するか**
という設計判断を扱う．両者を分けるのは，前者が「探索が何を返すか」を決めるのに対し
後者は返す値を一切変えず**応答時間とメモリ常駐だけ**を動かすためで，判断の根拠も
検証方法 (探索が 1 ノードもずれないこと) も別物になる．

## 12.1 なぜ独立した節が要るか

2026-08-12，「USI `go mate` で 1 手詰の初回応答が 4.856 秒かかる」という観測から，
**TT の確保コストが探索の実費を桁違いに上回っていた**ことが判明した．
機序は下の 3 つが積み重なったもので，どれも探索アルゴリズムの問題ではない:

1. ノード予算をそのまま TT サイズに流していた (§12.2)
2. 空 slot が全ゼロでないため `alloc_zeroed` に落ちず全バイトを書いていた (§12.3)
3. 確保が `go` の時間予算の内側で起きていた (§12.4)

**当初はテストの flaky として起票した**が
(`test_usi_go_mate_e2e` が全件実行でのみ `checkmate timeout`)，これは誤りだった．
「1 手詰に 5 秒はロジック上あり得ない．棋力にも影響する」というユーザ指摘を受けた
計測でエンジン側の欠陥と判明している．**症状がテスト側に出たときでも，実費に対して
桁が合わない時間はエンジンを疑う**という教訓としてここに残す．

## 12.2 サイズの決め方 — ノード予算は「見込み」であって「停止条件」ではない

主 TT の要素数は `search::tt_entries_for` が決める:

```
clamp(budget_nodes * 2, min_tt_entries, 1 << 23)
```

| 項 | 値 | 意味 |
|---|---|---|
| floor | `1 << 18` (主 TT 16MB) | production 探索の下限．leaf-mate は per-leaf の確保コストを下げるためこれを小さくする (`new_leaf_mate`) |
| ceil | `1 << 23` | 主 TT 512MB + 千日手表で計 704MB |
| 既定 | `RootDfpnNodes = 2,000,000` → 4M entries | 主 TT 256MB + 千日手表 96MB = **352MB** |
| 上書き | `TTSIZE` env | 計測用 |

**サイズの元は「どれだけノードを置く見込みか」であって「どこで打ち切るか」ではない．**
この 2 つは通常一致するので長らく同じ値を使っていたが，USI `go mate` で分離が必要に
なった — GUI は「この時間だけ考えて」と言うので停止条件は時間であり，ノード予算は
無制限 (`u64::MAX`) を置くしかない．これがそのままサイズ算出に流れると，
**1 手詰でも常に上限 704MB を確保して全バイト書く**．

したがって `DfPnSolver::set_tt_nodes_hint` で**サイズのヒントだけ**を渡す
(`rust/maou_usi/src/backend.rs`)．停止条件は時間と stop トークンのまま変えない．
ヒントが小さすぎても GC が低 amount エントリを間引くので，
**「解けない」ではなく「遅くなる」に落ちる** — これが停止条件と切り離してよい根拠である．

ノブは USI オプション `RootDfpnNodes` として公開する
([docs/commands/usi.md](../../commands/usi.md))．長手数を追うときはここを上げる．

### 既定 2M を下げる案 — 却下 (2026-08-12)

確保コストを下げる最も直接的な手は既定 `RootDfpnNodes` を下げることだが，**却下した**．

- 当初の動機だった確保コストは §12.3 / §12.4 で消えており，**残る対価は reach の縮小のみ**
  になった．
- 2M は `rust/maou_search/src/search.rs` が「~41 手級 (NN 盲点) の詰みまで捕捉できる予算
  (実測: 41te は ~1.2M ノード)」と根拠づけている値である．下げると捕捉できる詰みが減る．

メモリ制約環境で下げたい場合はノブがあるので，既定を動かす理由にはならない．

## 12.3 空 slot は全ゼロで表現する

`Entry` は現局面・親局面の持ち駒を**ビット反転して**保持する
(`rust/maou_shogi/src/dfpn/tt/entry.rs`)．空 slot の印 `NULL_HAND` は全 `0xFF` なので，
反転して格納すると**空 slot が全ゼロになる**．これにより `vec![null; n]` が
`alloc_zeroed` に落ち，OS のゼロページをそのまま受け取れる．

反転は表現だけの話で，`is_null()` が偽のときしか持ち駒が読まれないこと
(TT の全アクセス経路で確認済み) を前提に成立している．**探索の意味論は不変**．

**効果の切り分けに注意**: この全ゼロ表現で消えたのは**確保コストだけ**である．
プールからの貸し出し時の `fill` は 0.043s → 0.037s の 14% 改善にとどまった (§12.5)．

## 12.4 前払い — `isready` でプールを温める

TT は `solve` ごとに確保・破棄される．同じサイズの巨大バッファを毎回作り直すのは
無駄なので，要素数ごとのバケットを持つ `BufferPool` で使い回す
(`rust/maou_shogi/src/dfpn/tt/mod.rs`)．

さらに **初回の確保を `go` の時間予算の外へ出す**．`warm_tt_pool(root_dfpn_nodes)` を
`isready` の処理中に呼び (`rust/maou_usi/src/backend.rs`)，確保して即 drop することで
プールに載せる．次の `solve` は pool hit になり first-touch のページフォルトを払わない．

これは [1局面探索エンジン設計 §5.1](../position-search/index.md) の
**「固定費は 1 手ぶんの予算を張る前に前払いする」**と同じ原則である
(あちらは TensorRT のエンジンビルド)．GUI は `isready` に時間制限を課さないので，
そこが固定費を払う場所になる．

**式は共有しなければならない．** `warm_tt_pool` と実際の `solve` が別々にサイズを
計算すると，温めたバケットと要求されるバケットが食い違い warm が**静かに**丸ごと
無駄になる (プールはサイズ別バケットなので失敗が表に出ない)．
そのため両者は `tt_entries_for` を共有する．

プールの上限は `DFPN_TT_POOL_BYTES` (既定 1GiB，プールごと) で，`0` を渡すと
プールを完全に無効化して従来どおり毎回新規確保する (A/B とメモリ制約環境の逃げ道)．
取りこぼしは `DFPN_TT_POOL_STATS=1` で鳴らせる — **足りなかったときだけ鳴る**設計で，
静かなら足りていると読む．

## 12.5 判断: 貸し出し時の `fill` は許容する (2026-08-12)

プールから貸し出すとき，バッファは初期値で `fill` される — 「確保直後の TT は全 null」
という不変条件を保つためで，これは **O(size)** である (既定 352MB で **0.037s/探索**)．

**この残コストは許容する．最適化しない．** 根拠:

1. **最適化余地が無い．** 352MB ÷ 0.037s = **9.5GB/s** で既にメモリ帯域に張り付いて
   いる．§12.3 の全ゼロ表現でも 14% しか動かなかったのはこのためである．
2. **残る手段の対価が大きい．** `fill` を消すには世代スタンプで fill 自体を不要にする
   しかない．TT サイズを縮める案は §12.2 で却下した reach 縮小と同じ対価を払う．
3. **実戦では持ち時間に出ない．** dfpn は MCTS と別スレッドで並走するので wall clock に
   現れない (`go` 初手 = 0.502s = 予算ぴったりで確認済み)．消費するのは CPU 時間で
   あって持ち時間ではない．
4. **`go mate` では critical path に乗るが誤差．** 詰み探索の予算は通常秒オーダーなので
   37ms は無視できる．

**再開条件**: プロファイルで実害が見えたとき．その時点で世代スタンプ化を検討する．

## 12.6 効果 (実測 2026-08-12)

| 項目 | before | after |
|---|---|---|
| `go mate` 初回応答 (1 手詰) | 4.856s | **0.052s** |
| `go` 初手 (byoyomi 1000) | 1.889〜3.487s (予算超過) | **0.502s** (= 定常時と同値) |
| peak RSS | 745MB | 462MB |

**健全性の検証** — 本節の変更はすべて「探索が返す値を変えない」ことが主張なので，
検証も探索の同一性で行う:

- `test_29te` が canonical 396,516 ノード・同一 PV で通る (**探索が 1 ノードもずれない**)．
- `test_false_proof_hunt` を 2 シード (`GAMES=120/80`, `MATE1PLY_VERIFY=1`) で回して
  `FALSE_MATE(bug)` / `STRICT VERIFY None` ともに 0 件．

実行方法は [CLAUDE.md § 重いテスト](../../../CLAUDE.md) を参照 (release ビルド必須，
`--test-threads=1`)．

## 12.7 関連する仕様変更

`checkmate timeout` は「時間切れ」と「詰みは証明できたが手順を復元できない」の
2 つを畳んでいる (USI の `checkmate` は `<手順>` / `nomate` / `timeout` の 3 種しか
返せないため行そのものは変えられない)．本節の調査ではこの区別が付かないことで
切り分けが実測 50 回超に膨らんだため，`info string` で区別できるようにした．
詳細は [docs/commands/usi.md](../../commands/usi.md)．
