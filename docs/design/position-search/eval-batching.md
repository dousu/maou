# 評価バッチングの設計 — GPU 浪費の除去と棋力の関係

対象読者: 探索エンジンの GPU 性能を触る人．
関連: [index.md §3.3 バッチ収集](index.md) / [usi-engine/verification.md §5](../usi-engine/verification.md)

## 1. 目的とスコープ

**絶対的な指標は Elo (棋力)** であり，throughput はその代理変数に過ぎない．
本ドキュメントは「GPU の推論性能を最大限に引き出す」という目標を，
**棋力に届く経路と届かない経路に分けて**設計するためのもの．

スコープは評価バッチの生成・充填・GPU への渡し方．探索アルゴリズム本体
(PUCT・virtual loss・終端処理) は [index.md §3](index.md) が正．

## 2. 棋力に届かない 2 つの経路 (設計の出発点)

「GPU を速くしても強くならない」には**構造的に 2 つの形**がある．
どちらも実在するので，最適化を始める前に切り分ける．

### 罠 1 — 利得が対局間にしか出ない

対局をまたいで評価要求をまとめると self-play のスループットは上がるが，
**実戦は 1 局しかないので棋力は上がらない**．さらに A/B ハーネスは A と B が
同一プロセスで同一評価器を共有するため，**A/B の Elo 差としても現れない**．
得られるのは学習データ生成レートと実験の wall clock だけ (= 間接的 Elo)．

### 罠 2 — 対局内で埋めると質が落ちる

バッチを埋めるには backprop 前により多くの葉を集める必要があり，集めた葉は
すべて virtual loss を背負った古い統計で選ばれている．in-flight 葉 B 個と
木のノード数 N に対し **B/N が「PUCT が壊れている割合」**で，B を上げるほど
1 playout あたりの質が落ちる．**速度 ↑ × 質 ↓ の積が Elo なので最適点がある**．

## 3. 実測 — 何が律速なのか

`cargo run --release -p maou_search --example nps_bench`．平手 startpos，
leaf_mate off / root_dfpn off，seed 42 (2026-07-28)．MockEvaluator なので
**NPS は探索コアの上限値であり GPU 実測とは比較しない**．読むのは fill%
(`avg_batch ÷ batch_size`) と `eval_batches` (= GPU 呼び出し回数)．

### 3.1 threads=1 では衝突していない

| playouts(要求) | batch | 実 playouts | avg_batch | fill% | collis% |
|---|---|---|---|---|---|
| 800 | 256 | 1,054 | 210.80 | **82.3** | 0.09 |
| 6,400 | 256 | 6,430 | 247.31 | 96.6 | 0.02 |
| 51,200 | 256 | 51,230 | 254.88 | **99.6** | 0.00 |

800 playouts の 82.3% は `(30 + 256×4) / 5 / 256` に一致する —
**最初の 1 バッチだけが木の広さ (平手 root の合法手 30) で頭打ち**になって
いるだけで，衝突由来ではない．

> **副次発見**: `--playouts 800 --batch 256` は実際には **1,054 playouts** 走る
> (+32%)．バッチを満たしてから予算判定するため．予算の解釈に効く．

### 3.2 threads を増やすと充填が壊れる

51,200 playouts / batch 256:

| threads | avg_batch | fill% | collis% | **eval_batches** |
|---|---|---|---|---|
| 1 | 254.88 | **99.6** | 0.00 | **201** |
| 2 | 69.18 | **27.0** | 1.42 | **743** (3.7 倍) |
| 4 | 16.79 | **6.6** | 6.56 | **3,052** (15.2 倍) |

threads=2 の衝突は 730 回に対し eval_batches は 743 — **ほぼ 1 バッチにつき
1 回の衝突**で，`search.rs` の収集ループが `Selection::Collision` で
`break` するため毎バッチが平均 69 件で打ち切られている．
TensorRT は `pad_to = batch_size` なので **GPU コストは呼び出し回数に比例**する．
これが「threads 2 はどの並列度でも約 4 割遅い」の機構
([verification.md §5.1](../usi-engine/verification.md))．

### 3.3 対局内 aggregator の上限利得は約 2.5%

T スレッドの部分バッチを 1 回にまとめても，得られるのは最良でも threads=1 と
同じ 255 件/回である．**aggregator が threads=1 に上乗せできるのは，CPU の
葉収集と GPU 推論のオーバーラップ分だけ**．

- 収集コスト: mock 実測 412k playouts/s ⇒ 256 葉あたり **≤ 0.62 ms**
- GPU バッチ: L4 実測から約 **25 ms**

⇒ **オーバーラップの上限は約 2.5%**．**「aggregator が 1 局の中で 2 倍を出す」は
成立しない**．

## 4. 2 倍差の分解

self-play 4,400 p/s と単発 30 秒探索 10,010 p/s の差
([verification.md §5.1](../usi-engine/verification.md)) は，対局間の
まとめ不足ではなく**手ごとの固定費**で説明できる:

| 要因 | 機構 | 見積 | 状態 |
|---|---|---|---|
| **完了検知のポーリング** | dispatcher が `sleep(100ms)` してから完了を見るため，探索が何 ms で終わっても最低 1 量子を払う | 約 1.2× | **除去済** (de15d54) |
| **root 評価が 1 件バッチ** | TRT では 1 件でも `batch_size` 件分のコスト．1 手あたり playout バッチ 4 回 + root 1 回 ⇒ **GPU の約 20% が 1 局面の評価** | 約 1.2× | `--pad-buckets` (既定 off) |
| **バッチ充填 82.3%** | §3.1．reroot 直後の最初のバッチが木の広さで頭打ち | 約 1.2× | 同上 |

いずれも **対局間 aggregator とは無関係**で，かつ**探索の挙動を 1 ビットも
変えずに**除去できる．

### 完了検知の実測 (release 同士，mock / dfpn off / 40 手)

| | throughput | wall | 1 手あたり |
|---|---|---|---|
| before (100ms ポーリング) | 8,043 p/s | **4.0s** | 100 ms |
| after (完了通知) | 278,457 p/s | **0.1s** | 2.5 ms |

**4.0s = 40 手 × 100ms ちょうど**．実配置では実 wall =
`ceil(T/100ms) × 100ms` なので，固定 800 playouts (T≈240ms) で **+25%**，
持ち時間 30s+0.5s (T≈890ms) で平均 **+5.6%** に相当する．

## 5. 設計 — 変更を 2 クラスに分ける

| | 検証方法 | 罠 2 の有無 |
|---|---|---|
| **クラス 1: 探索挙動が bit-identical な高速化** | throughput 実測 + bit-identical 回帰．**棋力 A/B 不要** — Elo は doubling 換算で導出 | **構造的に発生しない** |
| **クラス 2: 探索挙動を変えるレバー** | **持ち時間制の Elo A/B が必須** (§6) | 発生する．測って判定 |

### クラス 1

1. **探索完了の通知化** (実装済 de15d54)．完了は channel の切断で即時検知し，
   ポーリング間隔は進捗観測にのみ使う．observer の駆動間隔は不変．
2. **`pad_to` のバケット化** (`--pad-buckets`，既定 off)．実バッチ長を
   `pad_to` を上限とする 2 冪バケットへ切り上げる．shape 数は
   `log2(cap) + 1` に有界なのでエンジンビルドは発散しない．
3. (2 の後) root 評価を最初の playout バッチに相乗りさせる余地の検討．

### クラス 2

4. **バッチサイズの動的化** — B を木のノード数 N に比例させ B/N を一定に保つ．
   **速度レバーではなく質レバー**である．`pad_to` 固定の下ではコストが
   呼び出し回数に比例するため小バッチは逆効果で，**2 が入るまで動かせない**．
   バケット集合にスナップさせれば TRT の shape 数も増えない．
5. **衝突時の収集継続** (`Selection::Collision` の `break` 撤廃) と
   **対局内スレッド並列** — 2 と 4 の後に，まだ充填が足りない場合のみ．

## 6. 検証プロトコル

クラス 2 のレバーは以下 3 点セットで測る．E1 を省くと「速くなったが強く
なっていない」の原因が質の劣化か速度不足か区別できない．

| | 設定 | 測るもの |
|---|---|---|
| E1 | **等 playout** A/B | **質の劣化のみ** (速度は無関係)．期待 ≤ 0 |
| E2 | **等時間** A/B | **正味の Elo** = 速度利得 − 質劣化 ← 判定はこれ |
| E3 | throughput 比 → 208 Elo/doubling で予測 | E2 実測と突き合わせて換算モデル自体を検証 |

- **A/B は `--parallel 1` で回す**．並列対局にすると 1 手の wall clock が
  他対局の GPU 負荷に依存し，持ち時間制の測定が汚染される．
- **n の見積り**: n=40 の検出限界は約 150 Elo．±50 Elo を 95% で分離するには
  **ペア局面込みでも n ≈ 90-190 局**が要る．クラス 2 に着手する前に，
  この対局数を払う価値があるかを期待効果から判断する．

## 7. 将来の改善余地 — self-play の効率化 (棋力とは別枠)

**当面の方針は棋力を直接狙うこと**であり，以下は別枠の課題として残す．

対局をまたいで評価要求をまとめる **global collector** は，§3.3 のとおり
1 局の棋力には効かないが，**self-play のスループットには効く**．
並列自己対局は現状 parallel 1→8 で **1.257 倍**で頭打ちである一方，単発の長い
探索は 1.8-2.0 倍速い．各対局が既にほぼ満杯のバッチを作っているため，
`Mutex<Session>` での直列化と手ごとの固定費が残差になっている．

価値が出るのは次の 2 つで，**どちらも Elo の間接経路**である:

- **学習データ生成レート** — 同じ GPU 時間でより多くの自己対局棋譜が得られる．
  モデルが強くなる経路なので最終的には棋力に効くが，探索側の改善とは別の
  時定数で効く．
- **実験の wall clock** — A/B は n ≈ 90-190 局を要する (§6) ため，ここが
  速くなるとクラス 2 の判断を回せる回数が増える．

実装の当たりは [index.md §3.3](index.md) のとおり **同じ `Evaluator` trait の
背後**に置ける．ただし現行の `evaluate_batch` は同期・戻り値契約なので，
submit/await の分離 (oneshot channel など) か，呼び出し元がリーダーになって
合流待ちしてから GPU を叩く leader-follower のいずれかが要る．
**着手前に，クラス 1 を入れた後の parallel スケーリングを測り直すこと** —
手ごとの固定費が消えた後の頭打ちがどこかで，必要な機構が変わる．

## 8. 未検証事項

- **§4 の分解は GPU 未確認**．CPU の mock 測定が保証するのは
  fill/衝突/呼び出し回数という**構造量だけ**である．
- **MockEvaluator では棋力を語れない**．prior/value が擬似乱数で探索が収束
  すべき信号が存在しないため，bestmove 一致率は質の証拠にならない．
  ローカル CPU は 23 p/s なので実ネットでの Elo 測定は原理的に不可能．
- **TRT の shape ごとのエンジン構築コストとキャッシュ挙動は未測定**．
- **バケット化で出力が bit-identical のままかは未確認**．現在の
  「並列度を変えても bit-identical」は **`pad_to` 固定で shape が常に同一**で
  あることに依存している可能性があり，バケット化はこの再現性を壊し得る．
  **既定化の前提条件として GPU で先に確認する**．
