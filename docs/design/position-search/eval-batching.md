# 評価バッチングの設計 — GPU 浪費の除去と棋力の関係

対象読者: 探索エンジンの GPU 性能を触る人．
関連: [index.md §3.3 バッチ収集](index.md) / [usi-engine/verification.md §5](../usi-engine/verification.md)

## 1. 目的とスコープ

**絶対的な指標は Elo (棋力)** であり，throughput はその代理変数に過ぎない．
本ドキュメントは「GPU の推論性能を最大限に引き出す」という目標を，
**棋力に届く経路と届かない経路に分けて**設計するためのもの．

スコープは評価バッチの生成・充填・GPU への渡し方．探索アルゴリズム本体
(PUCT・virtual loss・終端処理) は [index.md §3](index.md) が正．

**結論を先に**: 最大のレバーは `--batch-size` だった．**64 が 256 に棋力 A/B で
+137 Elo** 勝つ (§5)．対局間 aggregator は実装していない — 棋力には届かない (§2)．

## 2. 棋力に届かない 2 つの経路 (設計の出発点)

「GPU を速くしても強くならない」には**構造的に 2 つの形**がある．
どちらも実在するので，最適化を始める前に切り分ける．

### 罠 1 — 利得が対局間にしか出ない

対局をまたいで評価要求をまとめると self-play のスループットは上がるが，
**実戦は 1 局しかないので棋力は上がらない**．さらに A/B ハーネスは A と B が
同一プロセスで同一評価器を共有するため，**A/B の Elo 差としても現れない**．
得られるのは学習データ生成レートと実験の wall clock だけ (= 間接的 Elo)．

⇒ **対局間 aggregator を棋力の主経路から降ろす根拠はこれ**である
(充填率の議論ではない — §6.3 の訂正を参照)．

### 罠 2 — 対局内で埋めると質が落ちる

バッチを埋めるには backprop 前により多くの葉を集める必要があり，集めた葉は
すべて virtual loss を背負った古い統計で選ばれる．in-flight 葉 B 個と
木のノード数 N に対し **B/N が「PUCT が壊れている割合」**で，B を上げるほど
1 playout あたりの質が落ちる．

⇒ **実測では逆向きに効いた**．バッチを縮める変更 (256 → 64) は速度と質の
**両方**を改善し，棋力は速度換算値の 2.3 倍出た (§5.1)．

## 3. コストモデル (GPU 実測)

`maou search --playouts 6400` で `--batch-size` を振り，`elapsed_ms ÷ eval_batches`
を取った (Colab L4 / ViT 19.8M fp16 / TRT+CUDA / 2026-07-28)．
TensorRT は `pad_to = batch_size` なので **n = padding 後の長さ**である．

| batch (= padded) | ms/call |
|---|---|
| 8 | 1.13 |
| 32 | 2.85 |
| 64 | 5.39 |
| 128 | 10.95 |
| 256 | 25.47 |

```
cost(n) ≈ 0.15 + 0.084·n  [ms]     ← 固定費はほぼゼロ
```

30 秒の長い探索 (`cost(256) = 24.05 ms`) とも整合する．

**この式が本ドキュメントで最も重要な事実**である．固定費が無いので:

- **呼び出し回数を減らしても得はない** — バッチをまとめる施策 (aggregator，
  衝突時の収集継続) の速度上の価値は小さい．
- **効くのは padding を減らすことだけ** — 充填しきれない大きなバッチは，
  払った padding をそのまま捨てている．

## 4. 充填率 (fill) の実測

`avg_batch ÷ batch_size`．threads=1．

| 条件 | fill | collisions |
|---|---|---|
| 単発 30 秒 (317,826 playouts) | **99.5%** | 9 / 317,826 |
| `--playouts 6400` / batch 256 | 79.7% | 9 |
| `--playouts 800` / batch 256 | **35.1%** | 9 |
| `--playouts 6400` / batch 64 | 97% | 5 |
| `--playouts 6400` / batch 8 | 100% | 1 |

collisions が探索サイズによらず一定なのが手がかりで，
**「最初の 9 バッチが約 71 件で打ち切られ，以降は満杯」**と仮定すると一致する:

- 800 playouts: `9×71.3 + 256 = 897.7` → 実測 **898**
- 6,400 playouts: `9×71.3 + 23×256 = 6,529.7` → 実測 **6,530**

木が小さいうち (最初の約 640 playouts) だけ衝突が起き，抜けると満杯になる．
衝突は `search.rs` の収集ループが `Selection::Collision` で `break` することで
バッチを打ち切る．

**実 NN でしか起きない**: MockEvaluator は prior がほぼ均一なので降下が広く
散って同じ葉に当たらない．実 NN の prior は鋭く (平手 root で 2g2f 0.413 /
7g7f 0.237)，選択が上位手へ集中するため同じ葉へ何度も降りる (§6.1)．

## 5. 主レバーは `--batch-size`

### 5.1 棋力 A/B の実測 (2026-07-28, Colab L4 / 各 48 局)

`--ab-mode batch` / 持ち時間 30s+0.5s / `--parallel 1` / `--threads 1` /
`--opening-random-plies 8` / `--alternate-colors` / dfpn off:

| A / B | A Elo | paired t | 判定 |
|---|---|---|---|
| **64 / 256** | **+137 [+33, +241]** | **+3.19** | **64 の勝ち** (33W 0D 15L) |
| 32 / 64 | −22 [−119, +75] | −0.44 | 有意差なし |

色バランス (先手 23 / 後手 25) も残り持ち時間 (A 5.5s / B 5.4s) も公平．

**予測を 2.3 倍上回った**: throughput +34.1% を換算すると +59 Elo
(1 doubling ≈ **+140 [+51, +229]**，n=24) だが実測は +137．
差分の **+78 Elo 相当は 1 playout あたりの質の向上**と解釈できる — バッチを
下げると in-flight 葉が減って virtual loss の歪みが小さくなる (§5.3)．

⇒ **throughput からの Elo 換算は棋力の下界として扱うこと**．
バッチを縮める変更では質の向上分が上乗せされる．

### 5.2 速度 (2 つの独立な regime)

| batch | 単発 6,400 playouts | 持ち時間 30s+0.5s (各 4 局) |
|---|---|---|
| 8 | 7,096 nps | — |
| 32 | 11,131 nps | 9,918 p/s |
| **64** | **11,459 nps** | **10,257 p/s** |
| 128 | 10,685 nps | 10,039 p/s |
| 256 | 8,004 nps | 7,646 p/s |

32/64/128 はプラトー (±2%) で **256 だけが落ちる**．
同一 session の再現性も確認済み (スイープの batch 256 = 7,646 p/s と
別測定の batch 256 = 7,557 p/s が 1.2% 差)．

### 5.3 質も同じ方向に動く

`maou search` 6,400 playouts の root visits:

| batch | 2g2f | 7g7f |
|---|---|---|
| 8 | 4,556 | 969 |
| 256 | 3,999 | 1,527 |

batch を下げるほど **top-1 に集中**する = in-flight 葉が減って virtual loss の
歪みが小さい．CPU の mock 実験で見た平坦化が実 NN で再現した．

### 5.4 一般則

| batch | fill | 状態 |
|---|---|---|
| 8 | 100% | 充填は満点だが **GPU が遊ぶ** |
| 32 / **64** | 99% / 97% | **飽和点 = 最適**．両者に棋力差なし |
| 128 | 91% | わずかに padding 損 |
| 256 | 80% | **padding 損が大きい** → 64 に −137 Elo |

> **`batch_size` は「充填が飽和する最小値」に置く．**
> それより大きいと padding を捨て，小さいと GPU が遊ぶ．

L4 + TRT + ViT 19.8M fp16 では **64**．**別モデル・別 GPU では測り直すこと**
(最適値はモデルの計算量と GPU の並列度で決まる)．

**コードの既定値 8 は据え置いている**: CPU は padding が無くコストが実 items に
比例するため速度メリットが無く，質だけ落とす可能性がある．CPU での最適値は未測定．

## 6. mock で立てて実測に覆された仮説 (再発防止の記録)

CPU (MockEvaluator) での事前調査は**構造量なら転移する**と考えて進めたが，
3 件が GPU 実測で覆った．**転移するのは定常値だけで，立ち上がりは転移しない**．

### 6.1 「threads=1 では collision がバッチ充填を壊さない」→ 誤り

CPU では 800 playouts / batch 256 で fill 82.3% / collisions 0.09% だったが，
GPU (実 NN) では **fill 35.1% / collisions 9 回**．
原因は **mock の prior がほぼ均一**なこと (§4)．

### 6.2 「GPU 呼び出しに固定費 10ms がある」→ 誤り

800 playouts の 2 点から `cost(n) ≈ 10.3 + 0.052n` と外挿したが，
batch_size を振った直接測定 (§3) で否定された．固定費はほぼゼロ．
**2 点からの外挿を信じたのが誤り**で，短い 1 回の測定 (10 バッチ) では
GPU クロックの立ち上がり等が混ざる．
⇒ 「呼び出し回数を減らすことが最重要」という中間結論も撤回．

### 6.3 「対局間 aggregator の上限利得は約 2.5%」→ 根拠が誤り

「threads=1 の fill が 99.6% だから束ねる余地がない」と論じたが，
その 99.6% は 51,200 playouts の**定常値**で，実配置の短い探索では
fill 31-55% である．**結論 (棋力には効かない) は変わらないが理由が違う** —
正しい根拠は罠 1 (§2)．

## 7. `--pad-buckets` (計測用トグル，既定 off)

TensorRT の padding を `batch_size` 固定でなく 2 冪バケットへ切り上げる．
GPU で **+34.2%** (batch 256 / 800 playouts) を確認したが，**batch 64 の
上位互換にはならない**:

| | `--pad-buckets` (batch 256) | `--batch-size 64` |
|---|---|---|
| 速度 | +34% | +34% (同等) |
| 質 | 変わらず | **向上** |
| bit-identical | **壊れる** | **保たれる** |
| TRT エンジン | 9 個 + warmup 事前ビルド実装が必要 | 1 個 |

batch 64 では fill 97% でバケット化の余地がほぼ無い．
⇒ **既定化せず計測用トグルのまま残す**．

### bit-identical が壊れる証拠 (記録)

同一局面・同一モデルで `pad_to` の shape が変わると root 評価の出力が変わる:

| 手 | `--no-pad-buckets` (padded 256) | `--pad-buckets` (padded 1) |
|---|---|---|
| 2g2f | 0.4132 | **0.4151** |
| 7g7f | 0.2373 | **0.2346** |

PV も 7 手目から分岐した．**「並列度を変えても bit-identical」という性質は
`pad_to` 固定で shape が常に同一であることに依存していた**．

また，shape が増えるぶん TRT のエンジンビルドが増える．キャッシュが無い状態で
`--pad-buckets` を付けると **探索中に新しい shape に当たるたびに数十秒固まる**
(実測: 800 playouts の探索が 120 秒)．採用するなら **warmup で全 bucket shape を
事前ビルドする実装が必須**．

## 8. 手ごとの固定費 — 完了検知のポーリング (除去済)

dispatcher の monitor ループが `sleep(100ms)` してから `is_finished()` を見て
いたため，探索が何 ms で終わっても最低 1 量子を待ってから `bestmove` が返って
いた (実 wall = `ceil(T/100ms) × 100ms`)．

mock + dfpn off の自己対局 40 手で **before 4.0s (= 40 手 × 100ms ちょうど) /
8,043 p/s → after 0.1s / 278,457 p/s**．

GPU 実配置での効果 (dfpn off / `--parallel 1`):

| regime | before | after |
|---|---|---|
| 固定 800 playouts (8 局) | 4,399.8 p/s | **5,478.8 p/s (+24.5%)** |
| 持ち時間 30s+0.5s | 7,006.5 p/s | **7,556.6 p/s (+7.9%)** |

固定予算側は **plies 864 / playouts 724,528 / 空回り 49,056 が前 session の記録と
完全一致**しており，**探索の挙動を変えずに速度だけが上がった**ことを確認できる．

## 9. 将来の改善余地 — self-play の効率化 (棋力とは別枠)

**当面の方針は棋力を直接狙うこと**であり，以下は別枠の課題として残す．

対局をまたいで評価要求をまとめる **global collector** は，罠 1 (§2) により
1 局の棋力には効かないが，**self-play のスループットには効き得る**．
並列自己対局は parallel 1→8 で **1.257 倍**で頭打ちである一方，単発の長い探索は
1.8-2.0 倍速い．

価値が出るのは次の 2 つで，**どちらも Elo の間接経路**である:

- **学習データ生成レート** — 同じ GPU 時間でより多くの自己対局棋譜が得られる
- **実験の wall clock** — 棋力 A/B は n≈48 局 (約 1.7 時間) を要するため，
  ここが速くなると判断を回せる回数が増える

実装の当たりは [index.md §3.3](index.md) のとおり **同じ `Evaluator` trait の
背後**に置ける．ただし現行の `evaluate_batch` は同期・戻り値契約なので，
submit/await の分離 (oneshot channel など) か，呼び出し元がリーダーになって
合流待ちしてから GPU を叩く leader-follower のいずれかが要る．

**着手前に，`--batch-size 64` を入れた後の parallel スケーリングを測り直すこと** —
§3 のコストモデルにより「まとめて呼び出し回数を減らす」こと自体には価値が無い
ので，期待できるのは **CPU の葉収集と GPU 推論のオーバーラップ**だけである．
収集コストは 256 葉あたり ≤0.62 ms，GPU バッチ (batch 64) は 5.4 ms なので，
上限は **1 割程度**とみられる．

## 10. 未検証事項

- **CPU での最適 `batch_size` は未測定**．既定 8 を据え置く根拠は「padding が
  無いので速度メリットが無い」という機構的推論であって実測ではない
- **32 と 64 は n=48 で分離できなかった** (t = −0.44)．分解能は ±75 Elo
- **持ち時間モードのスイープは各 4 局**で，plies が 462〜621 とばらつく
  (対局の長さが throughput に混ざる)．32/64/128 が固まり 256 だけ外れる
  パターンは一貫しているが n は小さい
- **1 doubling ≈ +140 Elo は n=24** で CI [+51, +229] と広い
- **最適値はモデルと GPU に依存する**．別構成では §5.2 のスイープからやり直す
