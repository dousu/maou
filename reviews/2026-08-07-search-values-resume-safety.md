# 提案: `--resume` の蓄積保証と「探索値は training 側だけ」を文書化する

## 背景

user 質問: **`--resume` したときに同じ局面が探索される可能性はあるか．
重複なく貯まり，既探索の局面で時間を浪費しないようにしたい．**
**探索値は validation の前処理にも指定した方がよいか．**

実測して確かめたところ，`--resume` を付けている限り既探索の局面は
再探索されない (37 行 → 52 行，unique 52) が，**運用上の穴が 4 つ**見つかった．

## 見つかった穴 (いずれも実測)

| 穴 | 修正前の挙動 | 影響 |
|---|---|---|
| `--resume` の付け忘れ | **52 行の出力が 5 行に上書きされて全損** | 数日分の GPU 時間が消える |
| 出力に同一 id が 2 行 | `apply_search_values` の左 join が左の行を複製し，**3 行が 4 行に増える** | 学習データが静かに壊れる |
| 書き込みが非アトミック | フラッシュ中のクラッシュで出力が壊れる | `--resume` 不能 |
| 出力を入力ディレクトリ配下へ置く | 出力を HCPE として読もうとして `ColumnNotFoundError` | 実行できない |

4 つ目はテストを書く過程で発覚した (`--input-path` と `--output-path` が
同じディレクトリになる運用は自然にあり得る)．

## 運用の結論 (user 確認済み)

**`--resume` 単体で運用し，新しく始めるときは出力を手で消す．**

「初回は作り直し，以降は追記」を単一のコマンドラインで表現することは
原理的にできない．CLI には「これが初回か」を知る手段が無く，既存ファイルが
前の run の残骸なのか中断した同じ run の途中経過なのかを区別できるのは
実行する人だけである．既存出力が無ければ `--resume` 単体でも通るので，
スクリプトには `--resume` を固定で書いておけばよい．

## 実装 (src/)

| 変更 | 内容 |
|---|---|
| `--overwrite` を追加 | `--resume` も `--overwrite` も無いまま既存の出力を指すと**エラー**にする．出力は数日分の GPU 時間そのものなので取り違えで捨てさせない |
| `--resume` と `--overwrite` を排他に | 同時指定は**エラー**．実測では両方指定すると `--overwrite` が黙って無視され，作り直したつもりの実行で古い id (111/222/333) がそのまま残っていた．暗黙の優先順位を持たせない |
| `_merge` で id を一意化 | 重複時は後勝ち (新しい探索を残す)．落とした件数は警告に出す |
| `apply_search_values` で id を一意化 + 行数不変を検証 | 左 join の行複製を構造的に封じる．万一変わったら `RuntimeError` |
| 原子的な書き込み | 一時ファイルへ書いて `os.replace`．フラッシュ中にクラッシュしても壊れない |
| 走査から出力を除外 | `_hcpe_paths(input_path, exclude=output_path)` |

## 探索値は training 側にだけ適用する (user 質問への回答)

**検証データの前処理に `--search-value-path` を渡してはならない．**

1. **循環する** — 検証の教師がモデル自身の探索出力になると，
   「自分の探索を真似るほど良いスコア」になり汎化の指標として機能しない
2. **North-star とずれる** — 最終目標は実際の対局結果に対する較正である．
   検証を対局結果のままにすれば，検証損失は「未知の対局の実際の勝敗を
   どれだけ当てられるか」を測り続ける
3. **反証テストが成立しなくなる** — 反証テストは「value の過学習開始が
   epoch 11 より後ろへ動くか」である．epoch 11 という基準は 0/1 教師に対する
   `value_brier_score` 0.14949 で決まっているので，検証側の教師を変えると
   この数値と比較できなくなる

training と validation で教師の意味が違ってよい．検証損失の絶対値は前回と
比べにくくなるが，`value_brier_score` はどちらも 0/1 相手なので直接比較でき，
early stopping も同一 run 内の相対比較なので機能する．

`scripts/measure_calibration.py` は HCPE の `gameResult` を直接使い前処理を
経由しないので，held-out 較正の測定はこの選択の影響を受けない．

## 検証

- 単体 24 ケース (重複 id で行数が増えないこと / `_merge` の一意化 /
  `--overwrite` ガード / `--resume` と `--overwrite` の排他)
- 実データで真理値表を通した: 出力が無ければ 3 通りとも成功，
  出力があると「フラグ無し」だけエラー
- 実データで蓄積を確認: `--overwrite` で 2 行 → `--resume` で 4 → 6 行
- 実データで出力が入力ディレクトリ配下にあっても成功することを確認

## リスク

- **低〜中 / 破壊的**: 既存の出力を `--resume` 無しで指す実行が**エラーになる**．
  意図した挙動変更であり，従来は黙って全損していた
- **低 / 破壊的**: `--resume` と `--overwrite` の同時指定が**エラーになる**．
  従来は `--overwrite` が黙って無視されていたので，誤りに気づける方向の変更
- 版数は `maou 0.80.0` → `0.81.0` (CLI オプション追加 = feat 相当)
