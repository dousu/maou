# 提案: 会計修正後の GPU 再計測 (並列スイープ / 単発 NPS) と heap 破壊の再現条件を反映する

## Trigger

空回りを `playouts` から分離した (maou_search 0.23.0 以降) ため，`throughput` /
`nps` を含む過去の記録値が実探索量を表していない可能性があった．Colab L4 で
2 項目を取り直し，**§5.1 の結論は値を約 6% 下げたうえで維持できる**ことを確認した．
併せて，未解決だった `corrupted double-linked list` が**単発 `maou search` で
再現**し，並列とは無関係だと判った (再現コストが 15 分 → 30 秒になった)．

### 再計測 1: 並列スイープ (8 局 / 800 playouts/手 / max-moves 120 / dfpn off)

| parallel | 実 playout/秒 | 旧会計へ換算 | 旧記録値 | 差 |
|---|---|---|---|---|
| 1 | 4,399.8 | 4,696.9 | 4,681.6 | +0.3% |
| 2 | 5,331.6 | 5,692.3 | 5,643.5 | +0.9% |
| 4 | 5,530.5 | 5,905.2 | 5,882.4 | +0.4% |
| 8 | 5,536.4 | 5,909.7 | 5,879.2 | +0.5% |

空回りは消費予算の **6.34%** のみ (`--playouts 800` の短い探索では空回りが育たない
— 持ち時間モードの 99.3% と対照的)．**旧会計へ換算すると旧記録値を 1% 以内で
再現**するので，同一 regime の再測定として成立している．

- スケール上限は **1.257×** (旧 1.256×) で不変．
- 単発探索の上限との差は **1.97×** (旧換算 1.86×) → **aggregator の余地「約 2 倍」は
  会計修正後も維持**．
- `game time` (局ごとの合計) は parallel 1 → 8 で 163.6s → 1,037.2s = **6.3 倍**．
  wall clock は 1.26 倍しか縮まないので，**共有評価器での直列化**が可視化されている．
- 全設定で plies 864 / playouts 724,528 / 空回り 49,056 が **bit-identical** =
  並列度は探索結果を変えない (決定性の健全性確認)．

### 再計測 2: 単発探索 NPS (`--time-ms 30000 --threads 2 --root-dfpn`)

`playouts=303171 terminal_backprops=24 nps=10095 max_depth=28 repetitions=9`

- 空回りは **24 件 = 0.008%** → **静かな局面の単発探索に水増しは無く，物理上限の
  基準値 (約 11,000 playouts/秒) はそのまま使える**．
- `nps` は 10,095 で記録値 10,909 より **−7.5%**．空回りでは説明できない
  (0.008%) ため **session 間のばらつき**と解釈する (同じ threads 2．Colab は共有
  インフラで TRT キャッシュ状態も異なる)．**上限値は「約 10,100-10,900」と幅で
  持つ**のが正しい．

### 新事実: `corrupted double-linked list` は並列と無関係

再計測 2 の `maou search` (**parallel 相当 1 / 単一探索 / TRT+CUDA**) で，
`Stats` と盤面の出力が全て終わった**プロセス終了時**に発生した．従来は
「Colab の `--parallel 4` 終了時に 1 回」しか観測されておらず，並列自己対局が
疑われていたが，**単発探索でも起きる = 対局 driver・並列度は無関係**．
ONNX Runtime / TensorRT EP の teardown が疑わしいという既存の見立てを強めるとともに，
**30 秒で再現できる最小手順**が得られた．

## ドキュメント変更内容 (本レビューの承認対象)

### (a) §5.1 に会計修正後の再計測表を追記し，結論の数値を更新

上記の表 (実 playout/秒・旧会計換算・旧記録値) と，スケール上限 1.257×・
単発との差 1.97×・`game time` 6.3 倍の直列化シグナル・bit-identical の
決定性確認を追記する．**結論 (現行構成では aggregator を採用しない / 伸びしろ
約 2 倍は次 campaign の課題) は変更しない**．

### (b) §1 の実効速度へ幅と裏取りを追記

> 単発 30 秒の実測は **10,095-10,909 playouts/秒** (2 session の実測幅)．
> 空回りは 0.008% しかないので，この値は実探索量として読める
> (**物理上限のゲート値としては約 11,000 を使う**)．

### (c) §8.5 の `corrupted double-linked list` 項目を差し替え

> - **`corrupted double-linked list`** — **並列とは無関係**．単発の
>   `maou search --tensorrt --cuda` (parallel 1) でも，`Stats`・盤面の出力後の
>   **プロセス終了時**に発生した (2026-07-27)．従来は `--parallel 4` 終了時の
>   1 回だけだったため対局 driver を疑っていたが，driver も並列度も無関係と判明．
>   数値は出力後なので有効．DevContainer の mock では再現しない → ONNX Runtime /
>   TensorRT EP の teardown が疑わしい．**最小再現 (約 30 秒)**:
>
>   ```bash
>   maou search --sfen "lnsgkgsnl/1r5b1/ppppppppp/9/9/9/PPPPPPPPP/1B5R1/LNSGKGSNL b - 1" \
>     --model-path /content/model_fp16.onnx --tensorrt --cuda \
>     --threads 2 --batch-size 256 --time-ms 3000 --trt-cache-dir /content/trt_cache
>   ```
>
>   次の切り分け: (1) 同一コマンドを 3 回繰り返して決定的か確認，(2) `--tensorrt`
>   を外して `--cuda` のみで再現するか (再現しなければ TensorRT EP 側に確定)．

## 代替案と棄却理由

- **§5.1 の旧表を新値で置き換える**: 棄却．旧値は「会計が水増しだった時期の記録」
  として意味があり，**旧会計へ換算すると 1% 以内で一致する**ことが同一 regime の
  証明になっている．並記する．
- **`nps` の記録値を 10,095 へ書き換える**: 棄却．−7.5% は空回りでは説明できず
  session 変動と考えられるので，単一の値ではなく**幅**で持つべき．ゲート値
  (約 11,000) は据え置く．
- **heap 破壊を §8.5 から独立した節に格上げする**: 現時点では棄却．原因が
  外部ライブラリの teardown で，実害 (数値の欠損) が無いため既知課題の 1 項目で
  足りる．`--cuda` のみでの切り分けが済んでから格上げを判断する．
