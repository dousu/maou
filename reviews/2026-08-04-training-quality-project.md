# 提案: policy / value 改善プロジェクトを設計ドキュメント化し，Step 2 を実装する

## 背景

floodgate 棋譜のみで学習した Stage 3 モデルが，平手初期局面で勝率 0.71，
互角に近い中盤局面で 0.13 を返す問題を起点に，held-out 棋譜で系統的な
測定を行った．

学習期間 (2020-2025) 外の floodgate 2026-03 の 878 局 / 19,426 局面で
較正曲線を測ったところ，**ECE = 0.1127** の明確な S 字 (過信) が出た．
同じ測定を学習期間内 (2025-03-02) で行うと **ECE = 0.0319** であり，
**3.5 倍の汎化ギャップ**がある．学習データのラベルは当てられているのに
未知の局面では当たっていない = 記憶が起きている．

出現回数分布も測った．中終盤は **96.0% が出現 1 回**で，そのレコードが
持つのは policy = one-hot (1 サンプル) と value = 0/1 (1 ビット) だけ．
1 局 = 1 つの勝敗ビットが 110 局面に塗り広げられているので，独立な情報は
局面数ではなく対局数に等しい．

policy にも具体的な欠陥が出ている．複雑な局面の探索 (260k playouts) で，
探索が 80% の訪問を割いた手に policy は 5.9% しか置いておらず，
探索が却下する手に 40% 置いていた．

## 併せて実施したコード変更 (src/) — Step 2

| 施策 | 実装 |
|---|---|
| **対局単位の train/val 分割** | `--stage3-validation-data-path` を追加．指定時は `--stage3-data-path` の全量が学習に使われ `--test-ratio` は無視される |
| **early stopping** | `--early-stopping-patience` を追加．`dl.py` の `should_stop_early()` として判定を純粋関数に切り出し，テストで意味を固定した |

従来の分割は前処理出力のチャンクファイルをランダムに 1 割選ぶ方式だった．
チャンクは Zobrist hash 順に分割されているため同一対局の局面が train と val の
両方に入り，検証損失が楽観的に出ていた．その状態では early stopping を入れても
機能しないため，2 つは同時に入れる必要がある．

前処理は全コーパス横断で集約するため，**集約後に対局の同一性は復元できない**
(user 指摘)．したがって分割は前段 (棋譜 or HCPE) で行い，それぞれ前処理して
から渡す運用とする．

## 検討したが採用しなかった案

- **温度スケーリング (Step 1)**: 測定では T=2.70 で ECE 0.1127 → 0.0138，
  複雑な局面も −808 → −299 cp (参照 −336 cp) と改善したが，
  **根本原因の解決にならない**ため却下 (user 判断)．`T` が 1 に近いことを
  Step 2 の成功指標として使う
- **局面のサブサンプル**: 相関を減らせるが**序盤の統計を捨てる**ことになる
  (user 指摘)．却下
- **HCPE の `eval` 列**: クライアント依存のため却下 (user 判断)
- **`count` を損失の重みにする**: 集約前の尤度は `count` 倍なので現状の
  重み 1 は厳密には誤りだが，Step 3 でレコードの質が上がれば優先度が下がる．
  §6 未決に記載
