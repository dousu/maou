# 提案: 空回り 2 レバーの GPU 実測結果を verification.md へ反映し，§4.6 を「棄却」で閉じる

## Trigger

PR #409 マージ後の wheel で `--skip-proven` の発火量を GPU (Colab L4 / ViT 19.8M
fp16) で 2 regime 測った．**どちらも棋力 A/B に値する発火量ではなかった**ため
§4.6 を「GPU A/B 待ち」から「棄却」へ閉じる．同時に，**空回りが 99% でも探索速度
を奪っていない**という機構的な結論が得られた (これが本レビューの主要な追加情報)．

### 実測 1: 固定予算 (`--playouts 800` / 4 局 / `--max-moves 512`)

| | 実 playout/手 | 空回り/手 | 消費予算/手 | throughput |
|---|---|---|---|---|
| off (473 手) | 694.6 | 113.0 | 807.6 | 3,168.7 p/s |
| on (752 手) | 698.9 (**+0.6%**) | 82.9 (**−26.7%**) | 781.7 | 3,124.6 p/s |

空回りは消費予算の **14.0%** しかなく，全部消しても上限 +16%．

### 実測 2: 持ち時間モード (`--clock-ms 30000 --inc-ms 500` / 4 局)

126 件の偽証明を観測したのと同じ regime．**会計修正後に空回り比率を直接測った
初めての値**:

| | 実 playout/手 | 空回り/手 | 空回り比 | throughput |
|---|---|---|---|---|
| off (523 手) | 6,223 | **828,081** | **99.3%** | 7,006.5 p/s |
| on (444 手) | 6,334 (**+1.8%**) | 406,541 (**−50.9%**) | 98.5% | 7,031.3 p/s (**+0.35%**) |

**空回りを半減させても実探索は +1.8%，throughput は +0.35%**．期待効果は
+1.5 Elo で n=40 の検出限界 ~150 Elo の 2 桁下．

### なぜ効かないのか (機構)

**空回りは GPU の待ち時間を埋めているだけで，探索速度を奪っていない**．
1 手 0.89 秒で 828,081 回の走査 = 約 93 万回/秒の traversal を CPU が回している
一方，実 playout は 7,000/秒で **GPU の評価バッチ充填が律速**．走査は GPU が
評価している間の遊んでいる CPU 時間で起きるため，半減させても wall clock 上の
実探索はほとんど増えない．

⇒ **空回りは計測上の見かけの問題であり，性能上の問題ではなかった**．本 campaign の
実質的な成果は**会計の分離** (`throughput` / `nps` / `carried_visits` が実探索量を
表すようになったこと) であり，レバーは 2 つとも棄却する．探索速度の伸びしろは
§5.1 が既に特定している**バッチ aggregator (約 2 倍)** の側にある．

## 代替案と棄却理由

- **棋力 A/B を回してから閉じる**: 棄却．発火量が +1.8% では期待 +1.5 Elo で，
  n=40 (~150 Elo) でも n=400 (~30 Elo) でも検出できない．90 分の GPU 時間を
  「有意差なし」を得るために使うことになる．
- **§4.6 を削除する**: 棄却．「空回り 99% は性能問題ではない」は**再導出したく
  ない結論**であり，根拠となる 2 regime の実測ごと残す価値が高い (次に throughput
  の水増しを見た人が同じ道を辿る)．
- **`max_moves_to_draw` の確定化まで試してから閉じる**: 棄却．空回りを半減させて
  も効果が無いことが判ったので，残りの空回りを潰しても同じ結論になる．
